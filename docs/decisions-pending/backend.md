# Backend decisions and deviations (to merge into docs/DECISIONS.md)

| # | Topic | Sources say | What the backend does | Why |
|---|---|---|---|---|
| B1 | Capacity profiles for Epidemiologists | rbac.ts: analyst `capacity: none`. Docs D7 (to confirm): readable by every role that analyses. Docs D4: capacity chosen at analysis time | `/api/capacity-profiles` (management) follows rbac.ts exactly (analyst → 403). A read-only `/api/capacity-profiles/options` (id, name, beds, placeholder) is open to every non-admin role so comparison, results and geographic screens can pick a profile | Follows the matrix for the module while making the docs' analysis-time capacity check possible. **Confirm D7** |
| B2 | Report approver | Prototype: the analyst approves her own drafts. Docs D10 (proposed): author ≠ approver | Enforced by default (`REQUIRE_DISTINCT_APPROVER=true`). Seeded a second demo Epidemiologist, Dr. Sarah Icyeza (`s.icyeza@rbc.gov.rw` / `epi123`), to approve in the demo | The build brief asks for author ≠ approver; one login per role is not enough to demo it |
| B3 | Demo sign-in | Prototype switches role in the browser; brief: one seeded user per role | `POST /api/auth/demo-login {role}` issues a real JWT for that role's seeded demo user, only when `DEMO_MODE=true` (404 otherwise). Login page emails and passwords are kept (admin123, epi123, officer123, policy123) | Keeps the role switcher working against real server-side RBAC |
| B4 | Ebola marked provisional | Prototype engine: Ebola `provisional: false`. Docs Appendix A: provisional until reviewed. Brief: unreviewed values show "Provisional" | Both built-in presets are seeded `provisional=true`; their seeded approvals (from `parameterSets.ts`) are shown as "… (illustrative)" | Honesty rule; no epidemiologist review is recorded. Approving via `POST /disease-presets/{id}/approve {clearProvisional: true}` clears it explicitly |
| B5 | Preset fields | Prototype Disease Presets page: generic fields (R0, incubation, infectious days, mortality, asymptomatic, route) | Superseded by the SEIHFR schema (docs Module 4, D15), including route shares, baseline levers and per-disease HCW defaults (ppe before/after, recognition day, default initial cases). The custom `marburg-rw-2024` preset is converted: R0 1.4, incubation 7.5, other values from Marburg; R0 low/high set to 1.2/1.8 (not in the prototype) | One engine, one preset shape |
| B6 | Intervention levers | Docs Module 8 table | `engine_lever` values match the engine: contact_tracing, isolation, safe_burial, detection (testing), community (lockdown), masking (community + hospital), hospital, vaccination (shift). Only vaccination may use `shift` | Explicit, reviewable mapping per type row |
| B7 | Officers and the intervention library | rbac.ts: officer `interventions: full` | Officers' `interventions: full` covers local response plans (`/api/hospital/plans`), not the shared package library, which needs `presets: write` | Matches the prototype routes (`/interventions` → LocalResponsePlans for officers) |
| B8 | Saved scenarios are immutable | Prototype builder: new, clone, draft, view | Drafts change freely. A saved scenario's dataset, preset and package cannot change (409, "clone it"); name, description, visibility and suggested capacity can. Dataset version is pinned at save | Runs must stay reproducible |
| B9 | Deleting scenarios with runs | Prototype allows delete | 409 when the scenario has runs | Reports and comparisons reference runs |
| B10 | Running shared scenarios | rbac.ts: officer simulation `write` ("own and shared scenarios") | Any role with simulation ≥ write may run a scenario it can see (owner, admin, clone or view share) | Matches the comment in rbac.ts |
| B11 | Readable ids | Docs: uuid PK + readable code | Readable string PKs (`RUN-0100`, `SC-1052`, `RPT-033`, `APS-06`), allocated as max+1 | Same as X4 |
| B12 | What-if execution | Docs: what-if re-runs with fewer runs, labelled preview | Synchronous in the request: two reduced runs (`WHAT_IF_RUNS`, default 50) with the same seed, with and without the response; returns before/after for the district and national totals with `preview: true`. ~0.5 s each | Fast enough; no job polling needed |
| B13 | Health-worker what-if | Prototype page re-runs the engine with other protection settings | `POST /api/simulations/{id}/health-workers/what-if` re-runs (2 × `WHAT_IF_RUNS`) with changed `hcw` settings; preview | Replaces the in-browser engine call |
| B14 | Report export | Docs: async export job (queued → completed) | Generated synchronously in `POST /reports/{id}/exports` (~0.5 s), row still records status; ReportLab + matplotlib fan chart. PDF only | Simpler; same API shape |
| B15 | Population import | Prototype: browser-side checks, 2 GB files, background threshold 50 MB | Server checks every row with the same rules (`services/population_import.py`, ported from `utils/populationImport.ts`). Upload limit 50 MB in the MVP. Import runs in a background thread with job status; valid rows are aggregated to district totals to form a new dataset version; error rows are skipped and counted | MVP scope; the engine needs district totals only |
| B16 | Seeded population datasets | Prototype: dataset totals only | Each seeded dataset gets district rows from `data/geographic.ts` populations (approx. 2022 census, illustrative); RPHC5 total therefore becomes the district sum (13,221,609, not 13,246,394). Added "Rwanda districts (2022 census, approx.)" for geographic runs | Engine and geographic model need districts |
| B17 | District beds | Prototype geographic data: beds per district + bed multiplier profiles | Seeded as two capacity profiles with per-district rows ("MoH isolation beds - Q3 2026 (by district)", "Surge plan - +40% beds (by district)"), placeholder. Beds for a run = sum of the profile's rows for the run's districts, else `hospital_beds`; per-district beds fall back to population-proportional (docs Module 9) | Capacity applied at analysis time |
| B18 | Comparison saved records | Prototype `profileComparisons` reference runs that do not exist | Not seeded. Comparisons are computed on the fly (`GET /api/comparison`) or saved by users | No invented results |
| B19 | No seeded runs | Prototype seeds run history with in-browser results | No runs are seeded. `python -m app.seed --with-runs` optionally executes real engine runs for four seeded scenarios (≈4 s) | No invented results |
| B20 | Approved scenarios | Prototype `approvedScenarios` carry lever settings driving the browser engine | Seeded as illustrative approvals with their settings and no run. New approvals (`POST /scenarios/{id}/approve`) must link a completed run | Policy makers see real results for anything approved in the app |
| B21 | Response instructions issuer | Docs D9 open; rbac.ts: no `instructions` access for analyst or admin | `POST /api/hospital/instructions` allowed for Epidemiologists (`reports: full`), the docs' proposal | Needs a decision (D9) |
| B22 | Rt data sources | Docs: case datasets + quality issues | Seeded the two prototype series as case datasets (illustrative; the "Marburg Rwanda 2024 (reference)" series is not verified against a primary source). Quality issues (missing days, duplicates, negatives) are computed from the records, not stored | Always consistent with the data |
| B23 | Policy-maker approved scenarios / reports endpoint access | rbac.ts: policymaker `scenario: read`, `reports: read` | `/api/approved-scenarios` open to roles with scenario or dashboard access (not admin); `/api/reports` filters to approved + audience=policy for policy makers, approved + own hospital for officers, 404 otherwise | "Approval protects the audience" |
| B24 | Stale runs | Not specified | On startup, queued/running runs from a previous process are marked failed with a plain message | Threads do not survive restarts |
| B25 | Query parameter casing | — | camelCase query params (`capacityProfileId`, `runIds`, `datasetId`, `scenarioId`) to match bodies | Consistency with X3 |
| B26 | System health | Prototype page shows many metrics | Only real checks (DB, worker queue depth, run/import/report counts, durations, disk). Anything else on the page must be labelled demo by the frontend | Honesty |
| B27 | Inactive seeded users | Prototype users have no passwords | Non-demo seeded users get random unusable passwords; only the five demo accounts can sign in | No secrets in seed data |
