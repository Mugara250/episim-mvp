# F2b — scenarios, simulations, results (frontend)

| Topic | Sources say | What we did | Why |
|---|---|---|---|
| Results dashboard | Prompt: P0 "results dashboard (fan charts, key metrics, health-worker layer, Rt)". The prototype's `pages/Dashboard.tsx` + `components/Dashboard/*` drew invented forecast numbers (random trajectories, a fixed "R₀ 1.42", "HIGH risk") and no role could reach it | New `RunDashboard` (in `pages/RunResults.tsx`) at `/simulation/runs/:runId`. It keeps the prototype dashboard layout (6-tile row, analysis column, 320px sidebar) but shows only engine output. `pages/Dashboard.tsx` (the role fallback) now shows the latest completed run or an empty state. The fabricated components (`HeroSection`, `ViewModules`, `SidebarPanels`, `ContextTopBar`, `EpidemicTrajectoryChart`, `forecast.ts`, `types.ts`) are deleted | Honesty rules: no invented numbers. "Don't redesign": same layout and tile styling |
| Capacity on results | Docs D4: capacity is chosen at analysis time | Capacity profile selector on the results page (`?capacity=` in the URL). P(beds exceeded) and "beds run out from day N" come from the API for that profile; dashed beds line on the "Beds needed" chart | Capacity is a check, not an input |
| Model type and seed district | The prototype Run form had no model choice; docs Module 5 adds `model_type` and `seed_district_code` | Run form step 4 "Model": National SEIHFR or Geographic (30 districts). Geographic requires a seed district, limited to the districts in the scenario's dataset | P0 needs geographic runs |
| HCW settings on runs | Docs Module 15: the `hcw` object on the run request is optional | Optional step 5 in the Run form. Values start from the scenario preset's HCW defaults and are only sent if changed | Lets the HCW page start real runs with chosen settings |
| Health-Worker Layer page | The prototype ran the TS engine in the browser, with a disease toggle | The page reads a selected completed run (`?run=`) and shows its stored HCW results. Edited settings either give a reduced-run preview (`/health-workers/what-if`, labelled "Preview, not saved") or start a full run. The recognition-day table calls the what-if endpoint once per day | No engine in the browser (P0 rule); the preview is clearly labelled as reduced runs |
| Rt on results | Prompt: Rt in results | Rt is estimated from the run's median daily incidence (`/results/rt`) and labelled as such | Only per-run series are available |
| Rt Tracking page | Prototype: in-browser estimate, edits lost on reload, and a disease selector that switched dataset | Datasets, quality and estimate come from the API. Daily counts are saved (`POST records`); undo removes the user's last saved day. The disease comes from the dataset. A data-quality panel was added to the left card | DB-backed; the disease must match the dataset |
| Saved scenarios | Prototype: saved scenarios can't be changed; clone to change | Same. "Clone" in the builder = `POST /clone` (keeps lineage), then `PUT` with the builder's edits | Keeps `cloned_from_id` on the server |
| Deleting scenarios with runs | The prototype allowed any delete | The server refuses (409) when runs exist, and the toast shows its message | Runs and reports reference scenarios |
| Run history key figures | The prototype history had no figures | Each completed row shows cases and deaths (median and 5–95%) and chance of take-off. Failed rows show the server's message | Docs Module 5 "key figures" |
| Watched run in the URL | The prototype kept the active run in memory | `/simulation?run=RUN-0143` (also `?tab=history` and `?scenario=`) | Shareable, survives a refresh |
| Query keys | — | Reference lists use `['disease-presets']`, `['intervention-packages']`, `['intervention-types']`, `['population-datasets','options']`, `['capacity-profiles','options']` and `['geographic','districts']`, holding raw endpoint data (no transforms in `queryFn`) | Mutations on other pages refresh the builder. Workers sharing these keys must not transform data in `queryFn` |
| Scenario types | Prototype types had generic preset fields | `types/scenarios.ts` aliases the generated OpenAPI schema (`ScenarioOut`, `PresetOut`, `PackageOut`, `TypeOut`, `DatasetOut`). Builder cards show SEIHFR fields, the Provisional flag and the preset's reference | Decoupled from the presets worker's types |
| Cancel response | Docs: cancel a queued or running run | `POST /cancel` returns the run still `running` (the worker stops at the next day step); the page keeps polling until it shows `cancelled` | The worker checks a cancel flag |
