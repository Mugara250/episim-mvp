# F4b — officer pages, admin console, access requests

| # | Topic | Sources say | What we did | Why |
|---|---|---|---|---|
| F4b-1 | Officer/Admin/AccountRequest contexts | Prototype keeps all records in React state | Providers kept as pass-throughs (App.tsx unchanged); `useOfficer()` / `useAdmin()` compose TanStack Query hooks in `src/api/officer.ts` / `admin.ts`; mutations are async and surface server errors inline | Same page interfaces, data now in the database, scoped server-side (officer = own hospital) |
| F4b-2 | Hospital "today" | Prototype fixes today at 2026-10-08 (`data/hospital.ts`) | Uses the server date from `GET /hospital/me`; seeded entries end 8 Oct, so today's entry is new | Real dates. `data/hospital.ts` is kept only because `HealthWorkerLayer.tsx` (another worker's file) still imports it |
| F4b-3 | Local response plans delete | Prototype has create/edit only | Added a delete button (the API supports it) | Brief asks for database-backed CRUD |
| F4b-4 | Officer report export | Prototype downloads a .txt | Generates the server PDF (`POST /reports/{id}/exports`, then download) | One report renderer; the PDF carries the honesty line |
| F4b-5 | Account requests | Prototype keeps the requester's password in browser state and signs approved requesters in as the role's demo user | Server stores only the password hash; approval creates a real account. After a failed sign-in, Login.tsx looks up the request status by email (`GET /access-requests/status`); the demo-login fallback was removed. "Email in use" is checked by the server (409) instead of client-side | No plaintext passwords, real accounts. Small Login.tsx edit as allowed by the brief |
| F4b-6 | Access request status endpoint | Returned id, email, status, dates, reason | **Backend change:** `AccessRequestStatusOut` also returns `name`, `decidedAt`, `assignedRole` (`backend/app/api/auth.py`, additive; backend pytest green). The frontend reads it with a hand-written type, so `schema.d.ts` was not regenerated | The requester's banner says which role they were approved as |
| F4b-7 | "Notified" wording | Prototype toasts say the requester was emailed | Toasts say they can now sign in; System Health lists Email as "Not configured" | No email is sent in the MVP |
| F4b-8 | User form | Organisation is a free-text list (`ORGANISATIONS`) | Organisation is a real institution (`GET /institutions`); officers belong to their hospital. New users need an initial password (min 6); editing can reset it. `canEditBuiltins` is preserved on edit | The API stores `institutionId`, and accounts need a password |
| F4b-9 | Hospital districts | Hard-coded `RWANDA_DISTRICTS` list | Names come from the real boundary file (`GET /geographic/districts`) | One district reference |
| F4b-10 | Audit log filters | Client-side filtering of a static list | User, action and start date go to the server; the end date is filtered client-side (the API has no upper bound); the action list comes from the server | The server holds the log |
| F4b-11 | Roles & Permissions | Editable per-action checkbox matrix that nothing enforced | Read-only view of the `PERMISSION_MATRIX` access level per module, labelled as the matrix the server enforces | An editable matrix the server ignores would mislead |
| F4b-12 | System Health | All figures invented (uptime, response times, logs) | Banner, KPI tiles and service cards come from `GET /admin/system-health` (DB, worker, runs, disk, accounts). The 24h charts, log panel and maintenance mode have no backend: kept, labelled "Demo data"; fake "Restart" buttons removed; maintenance button disabled | Honesty rule; P2 |
| F4b-13 | Announcements | Static list with publish/expiry dates | Database CRUD (title, body, audience, level, published). Dates are not stored, so the date inputs were removed and "Preview" became "Save as draft" | The API has no date fields |
| F4b-14 | Support tickets | Static list with "Assigned to" and "View" | Database list with real counts and average resolution time, a status selector and a working CSV export. "Assigned to" removed (not stored) | The API has no assignee field |
| F4b-15 | Admin Settings | Five tabs of uncontrolled inputs | General tab is stored (`PUT /admin/settings/general`); session length and other runtime values are shown read-only from the server; Security, Email, Data & Storage and Integration tabs are labelled "Demo data" | Only general settings have a backing store |
| F4b-16 | User Settings page | Hard-coded profile ("Sarah Icyeza") with a save button; the icon reference rendered the page component itself | Profile shows the signed-in user read-only (admins edit accounts); Appearance labelled "Demo data"; fixed the self-referencing `<Settings>` icon bug | No self-service profile endpoint |
| F4b-17 | Deleted prototype data | `src/data/{hospitalEntries,hospitalReports,instructions,responsePlans,adminUsers,adminHospitals,auditLog,accountRequests}.ts` | Deleted; their content already lives in `backend/app/data/seed/*.json` | `backend/tools/convert_seed.py` (re-running the original export) would now need these files from git history |
