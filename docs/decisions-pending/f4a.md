# F4a — reports, approval, policy-maker pages, analyst dashboard

| Topic | Sources say | What we did | Why |
|---|---|---|---|
| Policy makers reading run results | Docs: policy makers see approved scenarios and approved reports. Backend `visible_run` only allowed the requester or users the scenario is shared with | `visible_run` also admits policy makers when the run is linked from a `ScenarioApproval` or an approved policy report (`approved_for_policy` in `backend/app/api/simulations.py`) | Without it, approved scenarios showed no results for policy makers unless the scenario was separately shared. Backend tests green |
| Report figures | Prototype drafts had only title/disease/scenario/summary | Editor adds report type, key points, recommendations and a "Based on" link to a completed run or saved comparison; figures are left empty so the server fills them from the run (median + 5–95% range) | Server is the single source of figures; keeps the ranges honest |
| Report link prefill | — | `/reports?run=RUN-…` and `/reports?comparison=…` open a new draft linked to it; the params are removed after use | Lets Simulations / Comparison pages hand off to reports |
| Editing a pending report | Prototype "Review" opened the editor | Saving a pending report returns it to Draft (server rule); added an explicit "Return to draft" action (`POST /reports/{id}/return`) | Matches the backend workflow; the notice says it needs resubmitting |
| Approver hint | Directive: name the approver account only if the API exposes it | The API does not, so the page just shows the server's 403 message and a static line "approved by someone other than its author" | No hard-coded account names in the UI |
| PDF export | Prototype generated PDFs/text in the browser (`utils/pdf.ts`, `utils/reportPdf.ts`) | Removed; every export is `POST /reports/{id}/exports` then an authenticated blob download | One renderer (server, ReportLab) with the honesty line, provisional flags and fan chart |
| Fallback `/reports` page (`Reports.tsx`) | Prototype template gallery backed by `lib/simulations` mock data | Replaced by the API list of approved reports (no current role reaches it; every role has its own page) | Removes a mock data path without redesigning a reachable page |
| Seeded approved scenarios | Prototype approved scenarios carried hand-set levers and were re-simulated in the browser | Seed rows have no run, so the cards say "Sample approval… no results are shown"; scenarios approved in the app (`POST /scenarios/{id}/approve`) show real run results and a fan chart | No invented results. **Gap:** there is no UI button yet for approving a scenario (it belongs on the scenario library page) |
| Policy dashboard 4th tile | Prototype: "Effect of response delay" comparing two hard-coded scenarios | "Chance it takes off" for the latest approved scenario with a run | The delay comparison needs two specific approved runs that may not exist |
| Analyst dashboard "Recent scenarios" | Prototype list of mock scenarios | "Recent simulation runs" from `/dashboard/analyst`; completed rows open `/simulation/runs/:id` | Real data; status badge gained Queued / Failed / Cancelled |
| Rt on dashboards | Prototype ran `estimateRt` in the browser | Analyst: `GET /rt/estimate`; policy maker: latest value from `/dashboard/policymaker` (policy makers have no `rt` access) | No engine code in the browser |
